# SUP-103 — Returning customer receives server error

## Customer

LegacyWorks Ltd

## Report

A returning customer can be found in the system, but checking product feature access results in an internal server error.

Affected user:

`robin@legacyworks.example`

The customer account has existed for several years and has only recently become active again.

## Reported behaviour

User lookup succeeds.

Feature-access requests fail with a server-side error.

## Expected behaviour

The application should determine whether the customer's account is entitled to the requested feature.

## Investigation

The issue was successfully reproduced for `robin@legacyworks.example`.

The user lookup endpoint returned the expected active user record, confirming that the user existed and could be associated with an account.

Feature-access requests instead returned a server-side error.

Structured application logs recorded `feature_access_error` for the affected requests.

The TypeScript request path was traced through `checkFeatureAccess()`. User lookup and account lookup completed successfully, after which the application attempted to evaluate the account's current subscription structure.

The affected account was inspected directly in MongoDB and compared with known-good customer accounts.

LegacyWorks Ltd stored `schemaVersion: 1` and used the historical fields:

- `plan`;
- `active`;
- `features`.

Current accounts used `schemaVersion: 2` and stored equivalent information beneath:

- `subscription`;
- `entitlements`.

The application expected the V2 structure and attempted to access `account.subscription.status`. The V1 document did not contain a `subscription` object, causing feature evaluation to fail before entitlement resolution could complete.

## Root Cause

The incident was caused by an unmigrated legacy MongoDB document whose persisted schema was incompatible with the application's current account model.

The TypeScript `Account` interface represented the expected V2 structure but did not provide runtime validation of existing MongoDB records. Typing the MongoDB collection as `Collection<Account>` therefore did not guarantee that historical documents actually conformed to the interface.

The immediate application failure occurred when current application logic accessed fields that did not exist on the V1 document.

## Resolution

A TypeScript schema-migration utility was implemented to migrate account documents from schema version 1 to schema version 2.

The migration:

- queried only documents with `schemaVersion: 1`;
- performed runtime validation before transforming each document;
- converted legacy subscription fields into the V2 `subscription` object;
- converted the legacy feature list into explicit boolean entitlements;
- incremented the schema version;
- removed obsolete V1 fields;
- updated the modification timestamp;
- used a guarded `updateOne()` filter;
- verified `matchedCount` and `modifiedCount`;
- re-read migrated records for post-update validation;
- logged successful, invalid and failed migration events.

A dry-run mode was implemented to preview transformations without modifying MongoDB.

## Validation

The dry run identified LegacyWorks Ltd as a V1 account and displayed the intended V2 transformation without modifying the document.

The live migration successfully migrated one document.

Post-migration inspection confirmed:

- `schemaVersion` changed from 1 to 2;
- `subscription.plan` preserved the original Pro plan;
- the active state was converted to `subscription.status: active`;
- `exportCsv` and `apiAccess` were enabled based on the legacy feature list;
- `auditLogs` remained disabled;
- obsolete V1 fields were removed.

The original feature-access request for `robin@legacyworks.example` subsequently succeeded for CSV Export and API Access and correctly denied Audit Logs.

Structured logs showed successful feature evaluation after migration rather than the original server-side error.

The migration was run a second time and found zero eligible V1 documents, demonstrating idempotent behaviour for already-migrated records.

Invalid-data handling was also exercised using a deliberately malformed V1 training record. The migration rejected and logged the invalid record without modifying it or aborting the entire migration run.

## Preventative / Systemic Improvement

Schema migrations should be incorporated into release/deployment procedures whenever persisted document structure changes.

Applications that consume long-lived MongoDB records should also perform runtime schema validation at appropriate trust boundaries rather than assuming TypeScript interfaces guarantee persisted-data shape.

Migration tooling should support dry-run execution, guarded updates, explicit schema versions, audit logging, invalid-record handling and post-migration validation.

Operational monitoring could additionally report counts of documents by `schemaVersion` so that unmigrated legacy records are detected before they generate customer-facing incidents.
