# SUP-102 — Unexpected Audit Logs access

## Customer

Acme Analytics

## Report

A review of customer access has identified that a Pro customer appears able to access Audit Logs.

Affected user:

`alex@acme.example`

## Reported behaviour

The Audit Logs feature is accessible.

## Expected behaviour

Audit Logs should only be available where the account's configured entitlements permit it.
## Investigation

The issue was successfully reproduced using the feature-access API for `alex@acme.example`.

The user record was present and active, and the linked account was found with an active subscription, ruling out user lookup, disabled-user, missing-account and inactive-subscription causes.

Structured application logs showed that the request was evaluated as:

- feature: `auditLogs`
- subscription plan: `pro`
- result: allowed
- reason: `allowed`

The affected user's `accountId` was used to locate the corresponding Acme Analytics account in MongoDB.

Acme Analytics stored:

- subscription plan: `pro`
- subscription status: `active`
- `entitlements.auditLogs`: `false`
- `entitlements.apiAccess`: `true`

The stored entitlement was therefore correct and directly contradicted the observed behaviour. This distinguished SUP-102 from SUP-101: the data was right and the application was wrong.

The request path was then traced to establish where actual behaviour diverged from expected behaviour.

The feature name was read from the route parameter, validated against the known feature list, and passed to `checkFeatureAccess()` unmodified as `auditLogs`. Request routing was therefore not responsible.

`checkFeatureAccess()` cleared all preceding guards and delegated the decision to `resolveEntitlement()`.

`resolveEntitlement()` destructured the account's entitlements and rebuilt them into an intermediate lookup object. The `auditLogs` key of that object was populated from the account's `apiAccess` entitlement.

Entitlement resolution for `auditLogs` therefore returned:

- expected value: `false`
- actual resolved value: `true`

The `entitlement_disabled` guard was skipped and access was granted.

The behaviour was confirmed to be account-wide rather than user-specific, and not limited to the reporting customer.

All accounts were compared using MongoDB filters and projections. Three active Pro accounts stored `auditLogs: false` alongside `apiAccess: true`, and all three were incorrectly granted Audit Logs access:

- Acme Analytics;
- BluePeak Media;
- Orbit Retail.

Northstar Design and Vertex Systems were unaffected only because their `auditLogs` and `apiAccess` entitlements happened to hold the same value.

`exportCsv` and `apiAccess` resolved correctly for every account tested.

The LegacyWorks Ltd account could not be evaluated because it stores a `schemaVersion: 1` document. That failure occurs before entitlement resolution is reached and is tracked separately as SUP-103.

## Root Cause

The incorrect access behaviour was caused by a defect in the application's entitlement-resolution logic, not by inconsistent MongoDB data.

`resolveEntitlement()` rebuilt the account's stored entitlements into an intermediate `Record<FeatureName, boolean>` lookup object. Two of its three keys used property shorthand; the `auditLogs` key was written explicitly as `auditLogs: apiAccess`.

Audit Logs access was therefore decided by the account's API Access entitlement, and the stored `auditLogs` value was never read.

The defect was not detected by the type system. `Record<FeatureName, boolean>` constrains the key names and the value type, but both entitlements are booleans, so the transposed assignment satisfied the type checker.

The intermediate lookup object was itself unnecessary. It duplicated the shape of the `Entitlements` interface without any structural guarantee that each key resolved to its corresponding entitlement, which is what allowed a single-token mistake to become an entitlement bypass.

The fault is symmetric. An account storing `auditLogs: true` with `apiAccess: false` would have been incorrectly denied. No such account exists in the current data, so only the over-granting direction was observable.

## Resolution

The corrective action was a code fix. No MongoDB documents required remediation.

The intermediate lookup object was removed and `resolveEntitlement()` now indexes the stored entitlements directly:

```ts
export function resolveEntitlement(
    account: Account,
    feature: FeatureName
): boolean {
    return account.entitlements[feature] === true;
}
```

Because `FeatureName` and the keys of `Entitlements` are the same set of names, the feature name is used as the lookup key itself. There is no longer an intermediate structure in which a key and a value can be mis-paired, which removes the class of defect rather than the single instance.

The explicit `=== true` comparison ensures that a missing or non-boolean stored entitlement resolves to denied rather than to a truthy value.

The function was exported so that entitlement resolution can be asserted directly by tests.

Account data was re-read after the change and confirmed unchanged.

## Validation

A table-driven regression test was added at `src/accessService.test.ts`, asserting all three features against five entitlement fixtures.

The fixtures include two mixed cases in which `auditLogs` and `apiAccess` hold different values. These deliberately break the symmetry between the two entitlements; without them, a lookup that reads one in place of the other would still pass.

The test was confirmed to fail against the original implementation, failing both on the Pro fixture (incorrectly granted) and on the mixed fixture (incorrectly denied). It passes against the corrected implementation.

Post-fix validation confirmed:

- the original customer request returned `403` with reason `entitlement_disabled`;
- structured application logs recorded `feature_access_denied` for that request;
- BluePeak Media and Orbit Retail were likewise denied Audit Logs;
- Vertex Systems, which stores `auditLogs: true`, continued to receive Audit Logs access;
- CSV Export and API Access results were unchanged for every account tested;
- the Free account continued to be denied all three features;
- the MongoDB account documents were unchanged;
- `npm test` passed and `tsc` compiled without errors.

## Preventative / Systemic Improvement

Avoid intermediate mapping structures in entitlement resolution. Where a feature name and its stored entitlement key are the same identifier, the stored object should be indexed directly so that no manual pairing step exists to get wrong.

Where such a mapping is genuinely required, it should be covered exhaustively by table-driven tests using fixtures in which the entitlements differ from one another. Fixtures in which all entitlements share the same value cannot detect a transposition.

Extend the structured access log to record the resolved entitlement value alongside the subscription plan. The log line for this incident recorded only the plan and the feature, which is indistinguishable from a legitimate grant; recording the resolved value would have made the divergence visible in the logs without code inspection.

Introduce a periodic entitlement reconciliation check comparing granted access against stored entitlements across all accounts, so that an over-grant is detected by monitoring rather than by customer access review.
