# SUP-104 — One user cannot be found

## Customer

Orbit Retail

## Report

One employee cannot access the product because the application reports that the user cannot be found.

Affected user:

`taylor@orbit.example`

A colleague at the same organisation can use the application normally:

`jamie@orbit.example`

## Reported behaviour

Jamie can be retrieved successfully.

Taylor receives "User not found".

## Expected behaviour

Both users belong to the same active customer account and should be retrievable.

## Investigation

The issue was successfully reproduced for `taylor@orbit.example`.

A colleague on the same Orbit Retail account, `jamie@orbit.example`, could be retrieved and could access entitled features normally. Orbit Retail itself was confirmed to be a healthy schema-version-2 account with an active Pro subscription.

Structured application logs recorded `user_lookup_failed` for Taylor and showed that the application attempted to query the lower-case address `taylor@orbit.example`.

Direct MongoDB queries established that no document matched that exact value. Querying Orbit Retail users by `accountId`, however, returned Taylor's intact active user document with the stored address:

`Taylor@Orbit.Example`

Jamie was stored as `jamie@orbit.example`.

The application normalised every incoming email address to lower case before executing an exact MongoDB lookup. MongoDB string equality was case-sensitive, and the users collection had neither a case-insensitive collation nor an email index providing alternative matching behaviour.

As a result, Jamie's lookup succeeded because his stored value was already in the canonical lower-case form expected by the read path. Taylor's record was unreachable because every possible request was converted to lower case before querying a mixed-case stored value.

## Root Cause

The incident was caused by asymmetric email normalisation between application reads and persisted data.

The read path canonicalised email addresses to lower case before querying MongoDB, but the write path did not enforce the same canonical representation.

The database therefore legitimately contained `Taylor@Orbit.Example`, while the application could only query for `taylor@orbit.example`.

The defect affected one of the current seeded users but could recur for any future mixed-case email written without normalisation.

The investigation also identified a related data-integrity risk: because `users.email` had no unique index, case variants of the same logical email address could coexist as separate documents.

## Resolution

Email canonicalisation was centralised in a reusable `normalizeEmail()` function that trims surrounding whitespace and converts addresses to lower case.

Application lookup routes were changed to use the shared canonicalisation function, and normal data-write paths were changed to canonicalise email values before persistence.

A reusable TypeScript data-cleanup utility was implemented to identify existing non-canonical email addresses and convert them to the canonical representation.

Before updating a user, the utility checks whether another document already owns the target canonical email. Potential collisions are logged and skipped rather than being merged or overwritten automatically.

Updates use guarded filters containing both the user `_id` and the previously inspected email value. Updated records are re-read after modification to validate the result.

A dry-run mode allows proposed changes to be reviewed before writes occur.

## Validation

The dry-run identified Taylor's mixed-case address without modifying the database.

The live cleanup normalised one record from:

`Taylor@Orbit.Example`

to:

`taylor@orbit.example`

with no detected collisions.

Post-fix validation confirmed:

- lower-case, mixed-case and upper-case requests all resolved to Taylor's user record;
- Taylor could access CSV Export through the feature endpoint;
- Jamie continued to resolve and access the same account normally;
- Orbit Retail account data remained unchanged;
- structured logs showed successful user lookup and feature access after remediation;
- the cleanup operation was logged;
- normalisation unit tests passed;
- the TypeScript project compiled without errors.

## Preventative / Systemic Improvement

Canonical values should be enforced at every write boundary rather than only being normalised during reads.

All application paths that persist user email addresses should use the same central normalisation function.

A unique index should be added to the canonical `users.email` field after existing data has been audited for collisions. This would prevent duplicate logical identities from being stored under case variants.

Periodic diagnostics can additionally flag any non-canonical email values that enter the collection unexpectedly.
